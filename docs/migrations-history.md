# Разбор дыры в миграциях 000019–000023 и пустышки 000018

Дата разбора: 2026-09-14, трек T1 (ветка `track/t1`).

## Что удалось установить по истории git

История репозитория бэкенда состоит всего из **трёх коммитов** — она была пересоздана
(«squash» всей ранней разработки), поэтому промежуточных состояний в git нет:

| Коммит | Дата | Что добавил в `migrations/` |
|---|---|---|
| `c2f4259` | 2026-05-04 | `000001`–`000015` (пользователи, игры, сообщество, профиль, вики) |
| `3feadb2` | 2026-07-23 | `000016`–`000018`, `000024`–`000026` (wiki-reference, tabletop) |
| `f885b98` | — | миграций не трогал (CLAUDE.md, CORS) |

Ключевые факты:

1. **Файлы `000019`–`000023` в git не существовали никогда.** Ни в одном коммите
   ни одной ветки они не добавлялись и не удалялись (`git log --all --diff-filter=A/D`).
   Дыра появилась сразу в коммите `3feadb2`: он одним разом добавил `000016`, `000017`,
   `000018` (пустышку) и `000024`–`000026`.
2. **`000018_campaigns_vtt_scenes.js` — пустышка с самого рождения.** Она была
   закоммичена уже с `exports.up = () => {}` и комментарием «Placeholder: applied in
   some environments as a prior local migration. Keeps node-pg-migrate ordering aligned
   with the database history». Другой версии этого файла в git нет.
3. Сообщение коммита `3feadb2` — «Add tabletop, **campaigns**, wiki-reference modules» —
   но модуля `campaigns` в коммите нет и никогда не было (файлы никогда не удалялись).
   Это след того, что разработка велась вне git и в коммит попал уже «причёсанный» итог.

## Реконструкция (что, по-видимому, произошло)

В июле 2026 функциональность «кампании + сцены виртуального стола» разрабатывалась
**локально, без коммитов**. В локальной базе разработчика (и, возможно, на проде)
были применены миграции с номерами `000018`–`000023`: судя по имени
`campaigns_vtt_scenes`, они создавали таблицы кампаний и ранний вариант сцен VTT.
Затем код переработали: «кампании» как отдельный модуль исчезли, а стол свёлся к
`tabletop_rooms` + `tabletop_scenes` + `game_characters`. В git закоммитили только
финальные миграции, дав им номера `000024`–`000026`, чтобы **не конфликтовать с уже
записанными в чьей-то базе номерами 19–23**, а `000018` оставили пустышкой, потому
что в таблице `pgmigrations` какого-то окружения строка `000018_campaigns_vtt_scenes`
уже есть — без файла с таким именем `node-pg-migrate` отказался бы работать.

Названия и содержимое миграций `000019`–`000023` **восстановить из git невозможно** —
их там нет. Предположительно они создавали таблицы вида `campaigns`, `campaign_members`,
`vtt_scenes` (ранние имена), которые затем были заменены на текущую схему.

## Что покрывают 000024–000026

- `000024_tabletop_rooms_game_id` — колонка `game_id` (uuid, FK на `games`,
  ON DELETE CASCADE) + уникальный индекс в `tabletop_rooms`: комната стола привязана к игре.
- `000025_create_tabletop_scenes` — таблица `tabletop_scenes` (сцены стола:
  фон-карта, токены, состояние; используется модулем `tabletop` и WebSocket).
- `000026_create_game_characters` — таблица `game_characters` (связка
  игра ↔ персонаж ↔ игрок, уникальность персонажа в игре).

То есть вся функциональность «виртуальный стол + персонажи в игре», которую могли
создавать пропавшие миграции, в текущей схеме покрыта миграциями 17 + 24–26.

## Проверки, выполненные локально (2026-09-14)

1. **Чистая накатка воспроизводима.** `npm run migrate:up` на пустой базе
   `dnd_hub_t1` прошёл без ошибок: 21 миграция, 33 таблицы.
2. **Схема совпадает с рабочей базой разработки.** `pg_dump --schema-only` для
   `dnd_hub` (пересоздана с нуля 2026-09-14, полный e2e-прогон зелёный) и для
   `dnd_hub_t1` — **идентичны** (расходятся только случайные служебные токены
   `\restrict` в шапке дампа).
3. **Код и схема согласованы на уровне таблиц.** Просмотрены все `FROM / JOIN /
   INSERT INTO / UPDATE / DELETE FROM` в `src/` — каждая упоминаемая таблица
   создаётся миграциями. Совпадения вида `personal_games`, `current`, `older` —
   это CTE (временные подзапросы), а не таблицы. Таблица `community_lfg_posts`
   создаётся миграцией `000008`, но кодом сейчас не используется (LFG живёт в
   `community_posts`) — это не ошибка, просто мёртвая таблица.
4. Дополнительно дымовой тест (`npm test`, задача T1.6) прогоняет реальные запросы
   auth/games против этой схемы — зелёный.

**Критических расхождений «код требует — миграции не создают» не найдено.**

## Попутная критическая находка (исправлена в этом треке)

`npm run migrate:up` до исправления игнорировал `.env`: подключение бралось из
`migration-config.json`, где жёстко прописана база `dnd_hub`. Любой worktree-трек,
запуская «свои» миграции, на самом деле применял их к общей базе разработки.
Исправлено: скрипты миграций переведены на обёртку `scripts/migrate.js`, которая
читает `.env` через `src/config/env.js` (старые значения остались дефолтами, так
что на проде и в основном репозитории поведение не меняется).

## Чего может не хватать на проде — вопросы, требующие доступа к серверу

Доступа к прод-серверу у этого трека **нет**, поэтому ниже — не факты, а список
проверок, которые нужно выполнить на сервере (Ubuntu, postgres 16 в docker):

1. `SELECT name, run_on FROM pgmigrations ORDER BY id;` — есть ли на проде строки
   `000018`–`000023`? Если есть `000019`–`000023` — под какими именами? Файлов для
   них в репозитории нет, и следующий `migrate:up` на проде может отказаться
   работать или потребовать таких же пустышек.
2. `pg_dump --schema-only` прод-базы и сравнение с эталоном из этого документа
   (`dnd_hub_t1`). Особо смотреть: лишние таблицы вида `campaigns*`, `vtt_*` —
   осиротевшие следы локальных миграций; отсутствие `tabletop_scenes` /
   `game_characters` / колонки `tabletop_rooms.game_id`, если 24–26 на прод ещё
   не доехали.
3. Есть ли в прод-базе данные в осиротевших таблицах (если они есть) — решить,
   переносить или удалять.
4. Применялись ли на проде миграции руками (psql) в обход `pgmigrations`.

Пока эти проверки не сделаны, **нельзя** переиспользовать номера 000019–000023 и
нельзя удалять пустышку `000018` — на проде от них может зависеть порядок
`node-pg-migrate`.
